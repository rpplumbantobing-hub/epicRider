    56→## 2. Cross-context data principles
    57→
    58→All principles below apply to every bounded context in §3. Each is `PROPOSED` architecture unless it restates a control-file invariant (cited).
    59→
    60→### 2.1 Strong identifiers — `PROPOSED`
    61→
    62→- Primary key: **UUIDv7 or equivalent time-ordered 128-bit identifier** (`PROPOSED` — final standard via Phase 2 ADR, per `ARCHITECTURE.md` §9 "UUID/strong identifiers as decided in Phase 2 ADR"; physical encoding depends on OD-01).
    63→- Business identifiers (human-readable, context-scoped unique): e.g. document `doc_id` (REQ-079), asset tag/QR code (REQ-036), opening code, invoice number. Business identifiers are separate columns with per-tenant uniqueness — never the primary key.
    64→- Rationale: time-ordered IDs support logical index locality and pagination without leaking counts; business IDs remain stable across merges/imports.
    65→
    66→### 2.2 Timestamp + actor attribution — control invariant (`ARCHITECTURE.md` §9; REQ-079, REQ-083)
    67→
    68→- Every mutable record carries `created_at`, `created_by`, `updated_at`, `updated_by` (server time, authenticated actor).
    69→- Records that participate in compliance/evidence flows additionally carry transition timestamps and the acting role in their history tables (e.g. `ApplicationStatusHistory`, `SignOff`, `DocumentVersion`).
    70→- Evidence metadata timestamps are server-side, not client-supplied (REQ-083; `DOCUMENT_EVIDENCE_MODEL.md` §5).
    71→
    72→### 2.3 Soft deletion only where semantically appropriate — control invariant (`ARCHITECTURE.md` §9)
    73→
    74→Explicit soft-deletion policy (`PROPOSED` mapping):
    75→
    76→| Category | Treatment |
    77→|---|---|
    78→| Approved/effective documents & versions, locked evidence, sign-offs, audit events, status histories, amendment chains, issued invoices/contracts, license & entitlement history | **Never deleted** — immutability + supersession/amendment (REQ-027, REQ-080, REQ-083, REQ-099) |
    79→| Assets, events, memberships, applications, recruitment openings | **Status-based lifecycle end-states** (retired/archived/removed/closed) — history preserved (REQ-045, REQ-049, REQ-063: closing recruitment must not delete application history) |
    80→| Drafts (technical rider, media kit, document draft, store listing draft), portfolio items, notification drafts | **Soft delete allowed** (`PROPOSED`) — `deleted_at`/`deleted_by` marker; restore possible |
    81→| User accounts | **Deactivation / anonymization**, not hard delete — attribution must survive; exact mechanics depend on privacy review (OD-09) |
    82→| Store listings | `archived` status per REQ-055 |
    83→
    84→Hard physical deletion occurs only via audited disposition (retention end-of-life, REQ-081, periods = OD-104) with tombstone records.
    85→
    86→### 2.4 Optimistic concurrency / versioning for mutable critical records — control invariant (`ARCHITECTURE.md` §9)
    87→
    88→- Mutable records that support concurrent editing carry a monotonic `version`/row-version attribute; conflicting writes are rejected and surfaced (never silently last-write-wins).
    89→- Applies at minimum to: document drafts (REQ-079 full change history), rundown items and chat editing (concurrency policy = OD-131), reservations (plus transactional overlap checks, REQ-065), store stock/price records (REQ-056 records old/new value per change), membership role changes, quota counters (transactional enforcement, §8).
    90→- Append-only histories (status histories, audit events) are the concurrency mechanism for lifecycle records: one transition per event, invalid transitions rejected server-side (REQ-064, REQ-080).
    91→
    92→### 2.5 Immutable approved records + amendment/version history — control invariant (MC §4; REQ-027)
    93→
    94→- Once a record reaches an approved/locked/effective state, its content is immutable via API (REQ-027 acceptance: approved record cannot be edited/deleted via API).
    95→- Corrections create a **new version** linked to the prior one, with mandatory reason and audit trail (amendment pattern; `DOCUMENT_EVIDENCE_MODEL.md` §6). Applies to: documents (REQ-080), evidence (REQ-083), quotations/contracts (commercial document principle, UC-4002), NCR/CAPA records after closure (UC-7008).
    96→
    97→### 2.6 Explicit tenant/workspace ownership — control invariant (MC §4; REQ-023)
    98→
    99→- Every tenant-scoped entity carries exactly one `workspace_id` (tenant owner). Cross-tenant CRUD must be rejected server-side (REQ-023 acceptance; `TESTING.md` typo correction: "CRUD lintas-tenant ditolak" — cross-tenant CRUD rejected).
   100→- Globally-scoped entities (User, AuthenticationMethod, Session, DeveloperRoleAssignment, AuditorAccessGrant, Platform catalog/products, CandidateProfile) are explicitly marked global in §3 and never carry `workspace_id`; their tenant visibility is derived through explicit relations (membership, application, grant scope).
   101→- Every query path is expressed tenant-first (see §9 access patterns); tenant context is a mandatory input to authorization (MC §2 effective access; `SECURITY.md`).
   102→
   103→### 2.7 Controlled migrations — REQ-029 (requirement, `PROPOSED`)
   104→
   105→- All schema changes via reviewed, versioned migrations; reversible where feasible; data-preserving by default; `db:push --accept-data-loss` style operations forbidden on environments with real data (REQ-029 acceptance). Details in §10.
   106→
   107→### 2.8 One platform, no parallel databases per tier — REQ-001 / REQ-002
   108→
   109→- A single continuous data foundation serves all tiers; tier growth enriches the same domain; parallel per-tier databases are forbidden (REQ-001 acceptance "no parallel DB per tier"; REQ-002 upgrade without data migration; historical W-5 rule of the superseded Phase-1 LICENSE_MATRIX, consistent with current baseline).
   110→- Tier differences are expressed through entitlement data (§3.5) and feature availability, **not** through separate stores or schemas per tier.
   111→
   112→### 2.9 i18n-ready text handling — REQ-028 (requirement; language default = OD-12)
   113→
   114→- Enum-like values (statuses, types, roles, tier names) are stored as **language-neutral codes**; display strings live in locale resource files, never in the data layer (REQ-028: no hard-coded UI strings; Indonesia default, EN-ready — OD-12).
   115→- User-authored content (rider text, chat, document content, profile text) is stored as entered, with optional `locale` metadata; translation of user content is out of scope (`PROPOSED`).
   116→- System-controlled nameable objects (role names, category names) carry a translation table or i18n key reference (`PROPOSED`).
   117→
   118→### 2.10 Auditability of sensitive transitions — control invariant (MC §4, `ARCHITECTURE.md` §9)
   119→
   120→- Every sensitive transition (auth events REQ-054, membership changes REQ-049, entitlement changes REQ-098/REQ-024 denials, document/evidence transitions REQ-080/REQ-083, store price/stock changes REQ-056, auditor access REQ-053, application decisions REQ-064) emits an append-only `AuditEvent` owned by the Audit context (§3.14).
   121→- Audit events are never editable/deletable via API; access to audit data is itself restricted and audited (OD-138, OD-164 govern retention/access parameters).

   125→## 3. Bounded context catalog (17 contexts, per `ARCHITECTURE.md` §3)
   126→
   127→Conventions for this section:
   128→
   129→- Entities are `PascalCase`; each is **owned by the context under which it is listed** (ownership = system of record). Entities referenced across contexts are noted as `(ref)` and never duplicated.
   130→- "States" are logical lifecycle states. `PROPOSED` unless a REQ cites the lifecycle verbatim.
   131→- Cardinality notation: `1—N`, `1—1`, `N—M`.
   132→- Tenant boundary: **Tenant-scoped** (carries `workspace_id`) or **Global**.
   133→- Access patterns listed per context feed the consolidated index strategy (§9).
   134→
   135→### 3.1 Identity
   136→
   137→**Purpose:** global user identity, authentication methods, sessions, recovery, and the two special global access grants (developer role, auditor access) that are deliberately NOT workspace memberships.
   138→
   139→| Entity | Purpose | Key attributes (conceptual) | Main relationships / cardinality | States | Key invariants (REQ) |
   140→|---|---|---|---|---|---|
   141→| `User` | Global identity of any human actor; NOT a workspace member by itself (REQ-025) | id, display name, primary contact, status, locale pref | 1—N `AuthenticationMethod`; N—M `Workspace` via `Membership`; 1—N `Session` | ACTIVE, DEACTIVATED, ANONYMIZED (`PROPOSED`; deactivation/anonymization mechanics = OD-09) | User != Membership != Role != Event Assignment (MC §4, TESTING.md); one user may hold different roles in different workspaces (REQ-025) |
   142→| `AuthenticationMethod` | A verified login channel: WhatsApp number or Google OIDC subject | id, user_id, method type, verified identifier, linked_at | N—1 `User` | LINKED, UNLINKED | Account linking must be safe/non-hijackable (REQ-022, REQ-047) |
   143→| `VerificationRequest` | One-time login/OTP challenge: single-use token, expiry, anti-replay | id, method, target, token hash, expires_at, used_at, attempt count | stands alone (produces `Session`) | PENDING, CONSUMED, EXPIRED, BLOCKED | Single-use, expiry, replay rejected, rate-limited, audited (REQ-021, REQ-054); vendor-agnostic (OD-03) |
   144→| `Session` | Active authenticated session/device | id, user_id, device label, created_at, expires_at, revoked_at | N—1 `User` | ACTIVE, EXPIRED, REVOKED | Revocation effective on next request (REQ-048); session policy params = OD-115 |
   145→| `AccountRecoveryFlow` | Controlled recovery across login methods without takeover paths | id, user_id, method used, verification evidence, outcome | N—1 `User` | OPEN, VERIFIED, FAILED, EXPIRED | No bypass of verification; audited (REQ-047, REQ-054) |
   146→| `DeveloperRoleAssignment` | Platform-level developer/portal role — separate from all workspace roles (REQ-052, REQ-031) | id, user_id, developer role, scope (which store functions), granted_by/at | N—1 `User`; no FK to `Workspace`/`Membership` | ACTIVE, REVOKED | Developer role cannot alter licenses/billing/broadcast (REQ-031); role model detail = OD-101 |
   147→| `AuditorAccessGrant` | Scoped, time-bound, read-only auditor access (REQ-053) | id, user_id, scope (workspaces/documents/evidence), granted_at, expires_at, read_only=true | N—1 `User`; scope refs to Workspace/Document | ACTIVE, EXPIRED, REVOKED | Auto-expiry; write denied; scope expansion = new grant with separate approval (REQ-053, REQ-044, REQ-084); parameters = OD-110 |
   148→
   149→- **Tenant boundary:** Global (no `workspace_id` on any Identity entity; `AuditorAccessGrant` reaches tenants only through its scope reference, which is enforced read-only).
   150→- **Auditability:** every auth attempt, recovery, session revoke, developer-role and auditor-grant change → `AuditEvent` (REQ-054, REQ-053).
   151→- **Access patterns & logical indexes:** `AuthenticationMethod` by (method, identifier) unique — login lookup; `Session` by (user_id, status), (session token); `AuditorAccessGrant` by (user_id, expires_at) for expiry sweeps; `User` by contact for invite/recovery resolution.
   152→
   153→### 3.2 Workspace/Tenant
   154→
   155→**Purpose:** the tenant root — the workspace/event organization that owns licenses, memberships, events, assets, documents.
   156→
   157→| Entity | Purpose | Key attributes | Relationships / cardinality | States | Key invariants (REQ) |
   158→|---|---|---|---|---|---|
   159→| `Workspace` | Tenant root (miniRider event workspace and above) | id, name, status, created_at/by, settings | 1—N `Membership`; 1—N `Event`; 1—1..N `License` (§3.5); 1—N `Asset` | ACTIVE, SUSPENDED, ARCHIVED (`PROPOSED`; suspension may follow license expiry per REQ-098/OD-108) | Tenant isolation root (REQ-023); max crew quota enforced at membership creation (REQ-009, OD-05) |
   160→| `WorkspaceProfile` | Presentation/branding of the workspace (target of the "workspace landing" extension) | id, workspace_id, branding, public visibility | 1—1 `Workspace` | DRAFT, PUBLISHED (`PROPOSED`) | Visibility/entitlement follows extension state (REQ-018) |
   161→
   162→- **Tenant boundary:** `Workspace` IS the tenant anchor; `WorkspaceProfile` tenant-scoped.
   163→- **Auditability:** workspace create/suspend/archive → `AuditEvent`.
   164→- **Access patterns & logical indexes:** `Workspace` by (owner user) via Membership; listing workspaces for a user = membership join (see §3.3); `WorkspaceProfile` by (workspace_id, published).
   165→
   166→### 3.3 Membership & Roles
   167→
   168→**Purpose:** the workspace membership lifecycle (kru/crew and owners), roles, invitations, and seats — strictly separate from identity (§4.1) and from event assignment (§3.4).
   169→
   170→| Entity | Purpose | Key attributes | Relationships / cardinality | States | Key invariants (REQ) |
   171→|---|---|---|---|---|---|
   172→| `Membership` | A user's membership of one workspace — NOT the user, NOT a role, NOT an assignment (REQ-025, REQ-049) | id, workspace_id, user_id, status, created/updated by/at, version | N—M `User`↔`Workspace` (materialized); 1—N `MembershipRoleAssignment` | INVITED, ACTIVE, SUSPENDED, REMOVED, LEFT (REQ-049: invite→accept→suspend→remove→leave) | Every status transition changes effective access immediately; removed member loses access on next request (REQ-049 acceptance) |
   173→| `Role` | Workspace-scoped role (owner, event manager, asset manager, finance, crew, …; dynamic roles on maxRider+ REQ-011) | id, workspace_id, name/i18n key, is_system | 1—N `MembershipRoleAssignment`; N—M `Permission` | ACTIVE, RETIRED (`PROPOSED`) | License ≠ role (prompt §8); role changes audited |
   174→| `Permission` | Permission vocabulary entry (e.g. event.edit, asset.dispatch) | id, code, description i18n key | N—M `Role` | ACTIVE, DEPRECATED | Deny-by-default; server-side enforcement (MC §4, REQ-024, REQ-026); full policy model = AUTHORIZATION_MODEL (Task 2-b) |
   175→| `MembershipRoleAssignment` | Which member holds which role | id, membership_id, role_id, granted_by/at | N—1 `Membership`; N—1 `Role` | ACTIVE, REVOKED | One user can hold different roles in different workspaces without conflict (REQ-025) |
   176→| `Invitation` | Secure workspace invite: signed, single-use, expiring token bound to workspace + offered role (REQ-051) | id, workspace_id, role_id, contact target, token hash, expires_at, used_at | N—1 `Workspace`; produces `Membership` on accept | PENDING, ACCEPTED, EXPIRED, REVOKED | Reused/expired links rejected; token cannot alter role (REQ-051); quota check at invite AND accept (REQ-009) |
   177→| `Seat` | Quota accounting unit linking memberships to entitlement (REQ-009; OD-05) | id, workspace_id, membership_id (nullable), state, allocated_at/released_at | N—1 `Workspace`; 0..1—1 `Membership` | AVAILABLE, ALLOCATED, RELEASED (`PROPOSED`) | Seat count ≤ tier quota + extension seats; enforcement server-side (§8; OD-05 owner-counting OPEN) |
   178→
   179→- **Tenant boundary:** all entities tenant-scoped.
   180→- **Auditability:** all membership/role/invitation/seat transitions → `AuditEvent` (REQ-049, REQ-051, REQ-009 denials audited).
   181→- **Access patterns & logical indexes:** `Membership` by (workspace_id, status) — team page; by (user_id, status) — workspace switcher; unique (workspace_id, user_id) active-membership constraint (re-invite of removed member = new row, history preserved); `Invitation` by (token hash) unique and (workspace_id, status); `Seat` by (workspace_id, state) for quota computation.
   182→
   183→### 3.4 Event & Assignment
   184→

   187→| Entity | Purpose | Key attributes | Relationships / cardinality | States | Key invariants (REQ) |

   190→| `EventAssignment` | Assignment of a member (kru) to an event — separate from Membership (REQ-050, REQ-007) | id, event_id, membership_id, role in event, schedule window, status | N—1 `Event`; N—1 `Membership` | OFFERED, ASSIGNED, DECLINED, COMPLETED, REVOKED (`PROPOSED`) | Crew sees only assigned events; context switch must not leak other events (REQ-007); double-assignment policy = OD-130; competency gate when required (REQ-074) |
   191→| `RundownItem` | Ordered timeline item of the event rundown (REQ-008) | id, event_id, sequence, time, title/notes, version | N—1 `Event` | PLANNED, LIVE/DONE, SKIPPED (`PROPOSED`) | Concurrent-edit policy = OD-131; optimistic versioning (§2.4) |
   192→| `EventChatMessage` | Team chat message within the event context (REQ-008) | id, event_id, author membership, body, attachments, sent_at | N—1 `Event` | SENT, EDITED, REMOVED (`PROPOSED`) | Only event-assigned members can read/write; attachments follow media policy (OD-137) |
   193→| `EventReport` | Field report/status update shared across the team (REQ-008 "update info/laporan antar tim") | id, event_id, author, content, timestamp | N—1 `Event` | DRAFT, SUBMITTED (`PROPOSED`) | Feeds event dossier (REQ-046) and evidence flows on ISOrider |
   194→
   195→- **Tenant boundary:** all tenant-scoped.
   196→- **Auditability:** assignment create/change/revoke, event state transitions → `AuditEvent`; unauthorized event access attempts denied + audited (REQ-050).
   197→- **Access patterns & logical indexes:** `Event` by (workspace_id, status, schedule) — event lists; `EventAssignment` by (membership_id, status) — "my assignments"; by (event_id) — crew list; reservation overlap queries join asset reservations to event schedule (§3.8); rundown by (event_id, sequence).

   199→### 3.5 Entitlement & License
   200→
   201→**Purpose:** the server-side entitlement engine inputs: which tier license a workspace holds, which capabilities exist, and derived effective access. License ≠ Capability ≠ Extension (§4.5).
   202→
   203→| Entity | Purpose | Key attributes | Relationships / cardinality | States | Key invariants (REQ) |
   204→|---|---|---|---|---|---|
   205→| `LicenseTier` | Reference enumeration of the ONLY three tiers: `miniRider`, `maxRider`, `ISOrider` | code | — | — | Closed enum; **hiRider is NOT a value of LicenseTier** (MC §1, TESTING.md); never extended without owner ADR |
   206→| `License` | A tier license held by a workspace (tenant) | id, workspace_id, tier, status, purchased_at, term start/end, renewal window, grace end | N—1 `Workspace`; 1—N `EntitlementGrant` | PURCHASED, ACTIVE, RENEWAL_DUE, EXPIRED, GRACE, DOWNGRADED (REQ-098: purchase→active→renewal→expiry→grace→downgrade) | Durations/gates = OD-108 OPEN; tier transitions audited (REQ-098); no data deletion on downgrade (REQ-099) |
   207→| `Capability` | Domain capability definition (recruitment, candidate discovery, CRM, asset scanning, audit mode, notification broadcast — MC §2) | id, code, description i18n key | 1—N `CapabilityRule` | ACTIVE, DEPRECATED | Capability is not a license (MC §2) |
   208→| `CapabilityRule` | Rule binding capability availability to tier/extension/role/context/object-state inputs | id, capability_id, condition set (tier set, extension set, role set, context, object states) | N—1 `Capability` | ACTIVE, SUPERSEDED | Evaluated server-side as part of effective access (MC §2 effective access formula; REQ-024) |
   209→| `EntitlementGrant` | Issued, versioned effective-right record (from a license and/or extension purchase; issued by commerce orders, §3.12) | id, workspace_id, source (license/extension/order), rights payload, valid_from/until, version | N—1 `Workspace`; refs `License`, `ExtensionInstance` | ACTIVE, SUSPENDED, EXPIRED, REVOKED | Issuance auditable (MC §6/§7 store issuance); grants drive `Seat`/quota (§8) |
   210→| `TierQuota` | Numeric limits per tier (crew count, storage, workspaces…) with parameter values | id, tier, quota code, limit value, unit | N—1 `LicenseTier` | ACTIVE | 5-crew base for miniRider (REQ-009); owner-counting = OD-05; commercial quotas = OD-06; values never invented (anti-hallucination) |
