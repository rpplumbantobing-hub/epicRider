   446→Source invariants: `MASTER_CONTROL.md` §1/§2/§4, `ARCHITECTURE.md` §4/§5/§6, `TESTING.md` "Mandatory domain invariants", `SECURITY.md`. Each item below states the invariant, its source, and the enforcement mechanism **in this data model**.
   447→
   448→### 4.1 `User != Workspace Membership != Role != Event Assignment`
   449→
   450→- Source: MC §4; ARCHITECTURE.md §4; TESTING.md Identity invariant; REQ-025, REQ-050.
   451→- Enforcement: four distinct entities in three distinct contexts — `User` (Identity, global), `Membership` + `Role`/`MembershipRoleAssignment` (Membership & Roles, tenant-scoped), `EventAssignment` (Event & Assignment, links Membership→Event). No foreign key path exists from `User` directly to `Event` or to `Role`; event data access requires BOTH an active membership AND an assignment (REQ-050 test matrix). Permission context is resolved through the chain `User → Membership → Role → Event Assignment → Permission Context` (ARCHITECTURE.md §4), which is exactly the relation ownership in §7.
