   192→   192→## 3.1 License dan entitlement
   193→   193→
   194→   194→Hanya ada tiga license tiers:
   195→   195→- `miniRider`
   196→   196→- `maxRider`
   197→   197→- `ISOrider`
   198→   198→
   199→   199→`hiRider` bukan license, bukan tier keempat, dan bukan nilai `license_tier`.
   200→   200→
   201→   201→Model akses konseptual yang dipertahankan:
   202→   202→
   203→   203→`License Tier + Active Extension + Capability Rules + Role/Permission + Resource Context + Object State → Effective Access`
   204→   204→
   205→   205→Security-sensitive authorization, tenancy dan entitlement nantinya harus ditegakkan di server/domain/API; menyembunyikan elemen UI saja bukan security control. Phase 3 hanya membuat pola UX/design-system yang mendukungnya; jangan mengimplementasikan seluruh authorization pada fase ini.
   206→   206→
   207→   207→## 3.2 Identitas, workspace dan recruitment
   208→   208→
   209→   209→Pertahankan pemisahan konseptual:
   210→   210→- User identity != Workspace Membership
   211→   211→- Workspace Membership != Event Assignment
   212→   212→- Recruitment Application != Workspace Membership
   213→   213→- Recruitment Application != Event Assignment
   214→   214→- Acceptance != Automatic Workspace Access
   215→   215→
   216→   216→## 3.3 Bahasa dan UI/UX
   217→   217→
   218→   218→- Bahasa default awal: Bahasa Indonesia.
   219→   219→- Pengguna dapat mengganti bahasa secara sistemik tanpa mengubah business logic.
   220→   220→- Semua string UI baru harus menggunakan mekanisme i18n, bukan hard-coded pada komponen.
   221→   221→- UI/UX adalah quality gate lintas fase: premium dan modern, konsisten, jelas, intuitif, minim langkah, responsif, aksesibel, serta berorientasi tugas.
   222→   222→- Setiap komponen/state yang relevan harus dapat menampilkan loading, empty, validation error, service error/retry, success, permission denied, expired entitlement, offline/sync state jika relevan, destructive confirmation dan progress state.
   223→   223→- Jangan membuat data, chart, metrik, status atau hasil palsu untuk membuat UI terlihat lengkap.

   252→   252→# 5. PHASE 3 IMPLEMENTATION — REPOSITORY FOUNDATION
   253→   253→
   254→   254→Perbaiki dan bentuk fondasi secara inkremental, sesuai stack yang terverifikasi.
   255→   255→
   256→   256→## 5.1 Engineering conventions
   257→   257→
   258→   258→- Pastikan package manager dan lockfile konsisten; gunakan mode install deterministik di CI.
   259→   259→- Sediakan script yang nyata dan bisa dijalankan untuk `lint`, `typecheck` (bila stack mendukung), `test`, `build`, dan format/check-format yang relevan.
   260→   260→- Tetapkan convention folder, penamaan, error handling, environment config, import boundaries dan public exports yang sesuai dengan pola repository.
   261→   261→- Tambahkan/perbaiki `.editorconfig`, `.gitignore`, formatting/lint rules, contoh environment configuration, dan dokumentasi developer seperlunya tanpa menambah duplikasi.
   262→   262→- Jangan menggunakan `ignoreBuildErrors: true`, disable lint/typecheck global, atau mock hasil test untuk menyamarkan kegagalan. Jika error lama menghalangi Phase 3, perbaiki bila masih dalam scope; jika tidak, catat baseline error, justifikasi, pemilik tindak lanjut dan gate yang harus dilewati. Jangan mengklaim quality gate lulus bila ia sengaja dilewati.
   263→   263→- Hindari instalasi dependency besar/duplikat; jelaskan alasan dependency baru.
   264→   264→- Jangan membuat abstraksi berlebihan atau arsitektur framework di atas kebutuhan yang belum ada.
   265→   265→
   266→   266→## 5.2 Design system foundation
   267→   267→
   268→   268→Buat/perbaiki design system yang terstruktur dan bisa dipakai konsisten pada fase berikutnya. Gunakan pendekatan yang sesuai dengan stack yang ditemukan, bukan asumsi framework baru.
   269→   269→
   270→   270→Minimal cakupan:
   271→   271→
   272→   272→### Design tokens
   273→   273→- warna semantic (foreground, background, surface, border, muted, primary, success, warning, danger, info);
   274→   274→- typography scale, font weights dan line heights;
   275→   275→- spacing scale;
   276→   276→- radius, elevation/shadow;
   277→   277→- responsive breakpoints;
   278→   278→- focus ring, transition/motion dan reduced-motion behavior.
   279→   279→
   280→   280→Jangan mengandalkan warna saja untuk menyatakan status. Pastikan kontras memadai dan state tetap terbaca dalam tema yang didukung. Pilih palette yang premium dan profesional tanpa mengorbankan kejelasan. Jangan menambah dark mode sebagai scope wajib jika belum ada keputusan/struktur yang tepat; bila existing, pastikan token konsisten.
   281→   281→
   282→   282→### Komponen dasar
   283→   283→Implementasikan hanya komponen umum yang benar-benar berguna, misalnya:
   284→   284→- Button: variants, sizes, disabled/loading;
   285→   285→- form controls: Label, Input, Select, Checkbox, Textarea dan validation help;
   286→   286→- Badge/Status indicator;
   287→   287→- Card/Surface;
   288→   288→- Alert/Inline message;
   289→   289→- Spinner/Skeleton/Progress;
   290→   290→- EmptyState;
   291→   291→- ErrorState dan retry pattern;
   292→   292→- PermissionDenied;
   293→   293→- dialog/modal atau confirmation pattern bila tersedia pada stack;
   294→   294→- Toast/notification pattern bila sudah sesuai arsitektur;
   295→   295→- layout/container/navigation primitives yang diperlukan untuk demo fondasi.
   296→   296→
   297→   297→Jangan membuat puluhan komponen tanpa kebutuhan. Gunakan semantik HTML/native controls bila tepat. Tetapkan API props/types dan dokumentasikan pola pemakaian.
   298→   298→
   299→   299→### Accessibility dan responsive behavior
   300→   300→- keyboard navigation dan focus terlihat;
   301→   301→- label dan accessible name yang benar;
   302→   302→- kontras yang memadai;
   303→   303→- semantic structure dan ARIA seperlunya, bukan menambahkan ARIA sembarangan;
   304→   304→- tombol/link/controls memiliki target interaksi yang wajar untuk touch;
   305→   305→- validasi/error tidak bergantung pada warna saja;
   306→   306→- hormati `prefers-reduced-motion` bila animasi ada;
   307→   307→- tes tampilan desktop, tablet, dan narrow mobile sesuai komponen/route yang dibuat.
   308→   308→
   309→   309→Jika tooling accessibility tersedia, gunakan. Jika tidak, lakukan pemeriksaan manual yang dapat direproduksi dan tulis keterbatasannya.
   310→   310→
   311→   311→## 5.3 i18n dari awal
   312→   312→
   313→   313→Implementasikan i18n yang cocok dengan router/framework yang benar-benar digunakan.
   314→   314→
   315→   315→Wajib:
   316→   316→- locale default `id` (Bahasa Indonesia);
   317→   317→- locale minimal yang didukung: `id` dan `en`;
   318→   318→- sistem pemetaan key-string yang terstruktur;
   319→   319→- language switcher pada showcase/shell fondasi bila terdapat UI;
   320→   320→- semua string UI baru—label, button, validation, empty/error/success state, navigasi dan metadata yang terlihat—diambil melalui i18n;
   321→   321→- penanganan fallback bila key hilang tanpa memunculkan error tak tertangani;
   322→   322→- tidak ada pergantian bahasa yang mengubah business logic atau permission;
   323→   323→- locale-aware formatting tanggal/angka/mata uang melalui API standar/localization library yang dipilih;
   324→   324→- aturan persistence bahasa yang aman dan konsisten dengan aplikasi (misalnya preference user bila identity tersedia nanti, dan fallback local preference/browser locale sebelum itu);
   325→   325→- hindari hydration mismatch atau server/client locale mismatch sesuai framework;
   326→   326→- dokumentasikan cara menambahkan bahasa dan cara mengaudit string yang masih hard-coded.
   327→   327→
   328→   328→Jangan mengarang copy bisnis yang membuat klaim produk/paket/standar. Gunakan teks placeholder yang netral pada showcase dan beri label yang jelas bila contoh bersifat demo.
   329→   329→
   330→   330→## 5.4 UI showcase / foundation route
   331→   331→
   332→   332→Sediakan satu halaman/route development showcase untuk menampilkan design tokens, base components, states, dan language switching. Jika sistem route tidak mendukung development-only route dengan baik, buat storybook-like page atau dokumentasi preview yang sesuai dengan stack.
   333→   333→
   334→   334→Showcase bukan business feature dan tidak boleh mengekspos informasi sensitif. Jika dapat diakses pada production build, pastikan tidak menampilkan debug secrets, user data, fake business metrics atau tooling internal.
   335→   335→
   336→   336→Tampilkan setidaknya contoh:
   337→   337→- typography, palette/token semantic dan spacing;
   338→   338→- button dan form control states;
   339→   339→- loading, empty, error/retry, success, permission denied;
   340→   340→- responsive behavior;
   341→   341→- Bahasa Indonesia ↔ English.
   342→   342→
   343→   343→Jika screenshot diambil, gunakan hanya sebagai bukti visual tambahan; jangan menyebut screenshot sebagai bukti test bisnis.
   344→   344→

   346→   346→
   347→   347→# 6. CI, TEST CONVENTIONS DAN QUALITY GATES
   348→   348→
   349→   349→## 6.1 CI pipeline
   350→   350→
   351→   351→Gunakan CI provider yang sudah ada. Jika tidak ditemukan, tambahkan pipeline minimal pada provider yang paling sesuai dengan repository hosting yang dapat dibuktikan; jika hosting tidak jelas, dokumentasikan asumsi dan pilih solusi yang mudah dipindah.
   352→   352→
   353→   353→CI sebaiknya menjalankan sesuai urutan:
   354→   354→1. install dependencies secara deterministik;
   355→   355→2. lint;
   356→   356→3. typecheck;
   357→   357→4. unit/component tests;
   358→   358→5. build;
   359→   359→6. accessibility/e2e smoke check bila tool dan test yang relevan tersedia.
   360→   360→
   361→   361→Ketentuan:
   362→   362→- tidak ada secrets di workflow atau logs;
   363→   363→- gunakan permissions minimum;
   364→   364→- versi runtime/tooling dipatok secara konsisten sejauh diperlukan;
   365→   365→- cache aman dan tidak menggantikan install/test;
   366→   366→- kegagalan quality gate membuat job gagal, bukan diabaikan;
   367→   367→- tidak boleh mengklaim pipeline berjalan di remote jika hanya diperiksa lokal;
   368→   368→- tulis nama workflow, trigger dan command yang dijalankan.
   369→   369→
   370→   370→Jika CI remote tidak bisa dipicu dari lingkungan ini, statusnya `NOT TESTED` atau `BLOCKED`, bukan `VERIFIED`.
   371→   371→
   372→   372→## 6.2 Test architecture
   373→   373→
   374→   374→Tetapkan konvensi yang sederhana, terpisah, dan terdokumentasi untuk:
   375→   375→- unit tests: fungsi/logic murni;
   376→   376→- component tests: states, interaction, accessible semantics dan i18n;
   377→   377→- integration tests: batas antar modul yang sudah ada;
   378→   378→- e2e/smoke: critical route/startup serta language switching bila dapat dijalankan;
   379→   379→- accessibility checks sesuai tooling/stack.
   380→   380→
   381→   381→Jangan menambahkan test framework kedua untuk pekerjaan yang sudah ditangani framework existing kecuali ada alasan eksplisit.
   382→   382→
   383→   383→Minimal tests wajib mencakup:
   384→   384→- semua locale memiliki key yang diperlukan oleh komponen showcase;
   385→   385→- fallback string/key yang hilang bekerja sesuai kebijakan;
   386→   386→- language switcher mengubah string yang terlihat tanpa mengubah route/logic yang tidak berkaitan;
   387→   387→- komponen Button, form control dan status memiliki disabled/loading/error states yang tepat;
   388→   388→- EmptyState/ErrorState/PermissionDenied menampilkan copy yang dilokalkan;
   389→   389→- interaksi dasar dapat dijalankan dengan keyboard untuk komponen yang relevan;
   390→   390→- main showcase route dapat dimuat;
   391→   391→- build/lint/typecheck commands benar-benar menjalankan tool yang dimaksud.
   392→   392→
   393→   393→Jangan menambah coverage threshold arbitrer jika baseline existing belum diukur. Bila threshold ditetapkan, jelaskan rasionalnya dan pastikan ia benar-benar ditegakkan.
   394→   394→
   395→   395→## 6.3 Testing evidence
   396→   396→
   397→   397→Untuk setiap command yang dijalankan, rekam:
   398→   398→- command lengkap;
   399→   399→- exit code;
   400→   400→- pass/fail dan ringkasan hasil;
   401→   401→- failure yang belum diselesaikan;
   402→   402→- batasan lingkungan dan test yang tidak dijalankan.
   403→   403→
   404→   404→Jangan membuat output test buatan, jangan mengedit laporan agar terlihat lulus, dan jangan menyamakan `build passed` dengan acceptance keseluruhan.

   442→   442→
   443→   443→- Pertahankan semua requirement Phase 1 yang benar-benar ada: `REQ-001` sampai `REQ-100` bila set tersebut dikonfirmasi di repository.

Jangan menciptakan requirement baru untuk menutup keputusan scope hiRider yang belum disetujui.

   448→   448→- Setiap perubahan keputusan arsitektur yang substantif harus memiliki ADR atau update keputusan dengan alasan, alternatif, konsekuensi, migration/rollback dan status.

   467→   467→# 10. DEFINITION OF DONE — PHASE 3
   468→   468→
   469→   469→Phase 3 hanya dapat dinyatakan `DONE` jika seluruh kriteria relevan berikut memiliki evidence:
   470→   470→
   471→   471→1. Satu control baseline yang kanonik dicatat; konflik antar control packs tidak lagi ambigu.
   472→   472→2. Remediasi F-01..F-08 ditriase dan statusnya didukung bukti; F-04 boleh tetap open hanya dengan impact dan owner decision yang jelas.
   473→   473→3. `MASTER_CONTROL.md`, `ROADMAP.md` dan `PHASE_STATUS.md` tidak saling bertentangan.
   474→   474→4. Commerce/store boundaries mengikuti tiga surface berbeda: License & Extension Shop, Public Store, Developer Equipment Store.
   475→   475→5. `PHASE_2_ACCEPTANCE.md` tidak memiliki centang PASS palsu; status Phase 2 mencerminkan hasil audit.
   476→   476→6. Referensi section Master Control yang aktif dapat ditelusuri ke section/anchor kanonik atau secara eksplisit menunjuk ke dokumen historis.
   477→   477→7. `HANDOFF.md` tersedia dan cukup untuk melanjutkan kerja.
   478→   478→8. Stack dan current-state baseline terdokumentasi, tanpa mengarang hasil.
   479→   479→9. Design tokens dan base components tersedia, konsisten, dapat digunakan ulang, responsif dan memperhatikan aksesibilitas.
   480→   480→10. Bahasa Indonesia menjadi locale default dan Bahasa Inggris bekerja melalui i18n; string UI baru tidak di-hard-code.
   481→   481→11. Test yang relevan untuk i18n, komponen dasar, keyboard/accessibility checks, dan showcase telah dijalankan atau statusnya jujur ditandai belum diuji/blocked.
   482→   482→12. Lint/typecheck/test/build scripts betul-betul menjalankan tool yang dimaksud dan tidak menyamarkan error.
   483→   483→13. CI dikonfigurasi dengan permission minimum, deterministic install, failure gates dan dokumentasi.
   484→   484→14. Tidak ada secret yang ditambahkan atau tercetak; perubahan konfigurasi aman dan terdokumentasi.
   485→   485→15. `PHASE_3_REPORT.md` mencantumkan files changed, commands, exit codes, evidence, limitations, blockers dan residual risks.
   486→   486→16. `ROADMAP.md` diubah ke status Phase 3 sesuai bukti saja; Phase 4 tidak dimulai otomatis.
   487→   487→
   488→   488→Jika suatu kriteria tidak terpenuhi, gunakan `PARTIAL`, `BLOCKED`, atau status yang tepat. Jangan mengubahnya menjadi `DONE` agar roadmap terlihat maju.

   493→   493→
   494→   494→Pada akhir eksekusi, tampilkan ringkasan yang jujur dan terstruktur:
   495→   495→
   496→   496→1. **Gate A — hasil audit konsistensi Phase 2:** status untuk F-01 sampai F-08, bukti utama, tindakan korektif, dan residual issue.

   503→   503→8. **Phase status:** status Phase 2 dan Phase 3 yang konsisten dengan ROADMAP.
   504→   504→9. **Next phase recommendation:** apakah fondasi sudah siap untuk Phase 4, beserta syarat yang masih harus dipenuhi.
   505→   505→10. **HANDOFF.md:** pastikan dibuat/diupdate di repository.
   506→   506→
   507→   507→Jangan membuat hasil fiktif. Jangan menyatakan remote CI sukses jika hanya konfigurasi file yang dibuat. Jangan mengklaim pentest, usability test, production readiness, certification atau full accessibility audit jika tidak benar-benar dijalankan.
